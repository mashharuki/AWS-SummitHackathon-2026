# AWS Summit Hackathon 2026 決勝向け現状分析レビュー

**作成日**: 2026-06-06  
**対象**: SABOROU リポジトリ全体、決勝プレゼン戦略、デモ準備、SWOT  
**レビュー方針**: 厳しめ。現状の強みより、決勝で失点し得る点を優先して指摘する。  

---

## 0. エグゼクティブサマリー

SABOROU は、技術的には決勝5チームの中でも十分に戦える素材を持っている。Bedrock Tool Use、Slack/Google文脈、3バンドガント、AI依存度ゲーミフィケーション、Lean形式検証、CDKによるAWS実装、AI-DLCの運用証跡は強い。

ただし、現状のまま決勝に出ると「便利なタスク最適化ツール」と受け取られるリスクが高い。予選フィードバックでも「人をダメにするより、最適化された人間を生んでしまうのではないか」と指摘されており、これはテーマ適合性の核心への疑義である。

最大の弱点はコード量ではない。ライブデモ信頼性、UI/UXの一撃性、15分決勝用のストーリー、そして「AIが気持ちよく判断力を奪う」というテーマの見せ切りが不足している。

結論として、決勝までの最優先方針は次の3つ。

1. **デモ完走性を証明する**: 実AWSでログイン、Slack、Google Calendar、Gantt、提案生成、AI依存度変化までを通し、E2E失敗状態を解消する。
2. **プレゼンを技術説明から体験劇に変える**: 「便利」ではなく「人間の判断力がやさしく退化する」物語として15分を設計する。
3. **見せる機能を絞る**: モック、未完成、説明が必要な機能は審査員導線から外し、1本の主人公ストーリーに集約する。

## 2. 決勝戦に向けて今のプロダクトに足りないもの

### 2.1 P0: ライブデモ信頼性の証明

現状最大の危険は、実AWSデモの成功証跡が弱いこと。`SESSION-HANDOFF-gantt-20260526.md` には「実AWSで全API呼び出しが401 Unauthorized」とあり、API GatewayのJWT authorizer段階で弾かれている可能性が記録されている。さらにAPI Gatewayアクセスログは無効で、authorizer拒否理由をログから取れないとも記録されている。

加えて、最新のPlaywright結果ファイルは `status: failed` を示している。これは決勝直前の評価としては非常に重い。コードや設計が良くても、審査員の前で動かなければ評価はほぼ消える。

**不足しているもの**

- 実AWSのクリーンなE2E完走ログ
- デモ用アカウント、デモ用Slackワークスペース、Google Calendarシードデータ
- 失敗時のバックアップ動画と即時切替手順
- API Gatewayアクセスログ、CloudWatchダッシュボード、アラーム通知

**決勝までの必須アクション**

1. `saborou.agentic-jp.com` でログインからタスク詳細までの手動チェックを毎日実行する。
2. Playwright E2Eを決勝デモ導線に合わせて1本に絞り、必ず緑にする。
3. API Gatewayアクセスログを有効化する。コスト削減よりステージ上の障害切り分けを優先する。
4. 本番デモと同一データで録画したバックアップ動画を用意する。

### 2.2 P0: 「最適化ツール」誤読への先回り

予選フィードバックでは、コンセプトや着眼点は良い一方で、「人をダメにするよりもむしろ最適化された人間を生んでしまうのではないか」と指摘されている。これは単なるコメントではなく、テーマ適合性の失点ポイントである。

SABOROUは、タスク整理、優先順位判断、危機管理、締切感覚をAIに委ねることで退化するという強い裏設定を持っている。READMEにもこの二重構造は書かれている。しかし、デモとプレゼンでそれが体験として伝わっていない。

**不足しているもの**

- 最初の60秒で言い切るテーマ定義
- 「AIに任せて楽になった結果、自分で決められなくなる」体験の可視化
- AI依存度スコアが上がる瞬間の演出
- 審査員の疑義に対するプレゼン中の先回り回答

**決勝用の主張**

> SABOROUは、仕事を最適化するサービスではありません。  
> 人間が本来持っていた「今やるべきかを決める力」を、AIが根拠付きで肩代わりし続けるサービスです。  
> 便利だから使う。使うほど判断しなくなる。これが、私たちの考える「人をダメにする」です。

### 2.3 P0: 15分決勝用ストーリーが未完成

現在の `demo-stories.md` は5分予選デモ向けであり、決勝15分の構成ではない。技術スライド `docs/slides/pitch-tech.md` は強いが、現状は技術アーキテクチャとAI-DLCの説明が中心で、共感導入、主人公体験、プロダクトの危険な魅力、デモの山場が不足している。

**不足しているもの**

- 15分用の決勝プレゼン台本
- 1本の主人公ストーリー
- スライドとライブデモの秒単位接続
- Q&A前に疑義を潰す構成

**推奨15分構成**

| 時間 | 内容 | 狙い |
|---:|---|---|
| 0:00-1:00 | Hook: AIで仕事は速くなった。でもやる量だけ増えた | 全員の共感を取る |
| 1:00-2:00 | テーマ反転: 便利になるほど判断力は退化する | 「人をダメにする」を定義 |
| 2:00-8:30 | Live Demo: Slack依頼、文脈読解、サボり提案、3バンドガント、AI依存度上昇 | 触りたい体験を見せる |
| 8:30-10:30 | なぜプロンプト芸ではないか: Bedrock Tool Use、心理学5理論、構造化出力 | 鶴崎さん、技術審査目線に刺す |
| 10:30-12:30 | AWS本番品質: CDK、サーバーレス、Cognito、DynamoDB、監視、テスト | AWS目線に刺す |
| 12:30-14:00 | AI-DLC実践: Lean形式検証、OSS PR、AIを人間が監督した証跡 | AI-DLCの勝ち筋 |
| 14:00-15:00 | Close: 人間の判断をやさしく奪うサービス | 記憶に残す |

### 2.4 P1: UI/UXの情報量がまだ多い

予選フィードバックでは、UI/UXが明確な課題として挙げられている。現コードを見ると、TaskListPageはシーズンバナー、週次チャレンジ、AI依存度、今日バナー、候補タスク、承認済みタスクが並び、TaskDetailPageは3ペイン、ガント、判定、チャット、ゲーム要素、実績、ストリーク、PvP/Guildモックまで含む。機能量は強いが、審査員が初見で「何を見ればよいか」を失う危険がある。

**不足しているもの**

- 決勝デモ専用の表示モード
- 一画面一メッセージの導線
- 「今日サボれる時間」と「AI依存度変化」を主役にする再配置
- モック機能を見せない判断

**推奨**

- 決勝デモでは設定画面、取扱説明書、PvP、Guild、ロードマップを見せない。
- タスク詳細画面は「ガント」と「サボローの提案」と「AI依存度」だけを見せる。
- 「これもできます」ではなく「この瞬間に人がダメになる」を見せる。

### 2.5 P1: 未完成またはモック機能の扱い

READMEでは、サボり癖レポートや本音データ蓄積が実装済み機能として見える。一方、`staticContent.ts` には「取説・ペルソナ・ロードマップはAPIが無いため、フロント側のベタ書き」とあり、Manualの初期データは空配列、進捗は0/100である。PvP/GuildもモックUIであることがREADMEに明記され、コード上も実機能なしと分かる。

これは悪いことではないが、決勝で「実装済み」として見せると危険である。

**判断**

- 取扱説明書を見せるなら、当日デモ用に本音データを事前投入して「育った状態」を表示する。
- それができないなら、取扱説明書は将来展望に下げる。
- PvP/Guildは審査員導線から外す。
- 「モックです」と言わなければならない機能は、基本的に決勝デモでは見せない。

### 2.6 P1: 技術差別化の測定可能な証拠

技術は強い。Bedrock Tool Use、SchedulePlannerAgent、SaboriProposerAgent、CDK、Lean形式検証、OSS PRは十分に差別化できる。ただし、現状の提案保存では `tokenCount: 0` がハードコードされており、コストやモデル使用量の観測ストーリーが弱い。

**不足しているもの**

- Bedrock呼び出し回数、平均レイテンシ、トークン数、成功率
- デモ当日のCloudWatchメトリクス
- 「AI-DLCでどれだけ速く、どれだけ安全に作れたか」の定量証拠

**推奨**

- 最低限、デモ用の運用ダッシュボードに以下を出す。
  - 提案生成回数
  - 平均生成時間
  - 失敗率
  - Bedrock呼び出し回数
  - E2E最終成功時刻

## 3. 審査員分析と有効なアプローチ

### 3.1 公開情報ベースの審査員/登壇者

公開資料では、QuizKnock関連として伊沢拓司さん、鶴崎修功さん、falcom/falconさんが示されている。AWS側の技術評価者も当然いると想定すべきだが、個人名が公開情報として確定していない場合は、AWS技術審査目線として抽象化して準備する。

### 3.2 伊沢拓司さん向け

**刺さるもの**

- 一言で人に話したくなるコンセプト
- 日常の共感
- 知的な面白さと笑い
- 「使ってみたい」と思える導入

**危険な失点**

- 技術説明が先に来る
- 「便利ですね」で終わる
- UIが複雑で、何が起きているか分からない

**有効な言い方**

> タスク管理ツールは、やることを増やします。  
> SABOROUは、やらない理由を作ります。

最初の2分は技術を封印し、Slackで依頼が積まれた主人公が「今日は寝かせていい」と許可される場面を見せる。伊沢さんには「これ自分も使いたい」と思わせるのが最重要である。

### 3.3 鶴崎修功さん向け

**刺さるもの**

- 仕組みの面白さ
- 論理的一貫性
- アルゴリズム、制御、検証
- 「プロンプト芸ではない」説明

**危険な失点**

- 心理学5理論が飾りに見える
- LLMにそれっぽい文章を出させただけに見える
- 暗号や形式検証で過剰な数学的主張をする

**有効な言い方**

> LLMに「サボってよさそう」と言わせているのではありません。  
> Slack/Calendarの文脈をContextSignalに落とし、Bedrock Tool Useで判定構造を固定しています。

注意点として、Q&A資料にある暗号関連の表現は慎重にする。固定長ハッシュに対して「単射性」のような強い主張をすると、数学的に刺される可能性がある。「衝突リスクと辞書攻撃リスクを設計上扱った」と表現する。

### 3.4 falcom/falconさん向け

公開情報だけでは詳細な評価傾向を断定できない。QuizKnock側の技術/開発/企画視点として考える。

**刺さるもの**

- 画面上で面白さが即時に分かる
- 「そこまでやるのか」と思える機能の深さ
- ステージ上でのテンポ

**有効なアプローチ**

- ガントチャートは「段取り表」ではなく「サボれる時間の発掘装置」として見せる。
- 依存度スコアは「メーターが増える」だけでなく、称号変化や一言演出で笑いに変える。

### 3.5 AWS技術審査目線

**刺さるもの**

- AWS上で動く本番デモ
- サーバーレス設計の必然性
- Bedrockの意味ある使い方
- セキュリティ、コスト、可観測性
- AI-DLCの人間監督証跡

**危険な失点**

- AWSサービスの羅列に見える
- API Gatewayアクセスログがない
- IAMが広い
- モック機能を本番機能のように語る
- AI-DLCを「使いました」で終わらせる

**有効な言い方**

> SABOROUは、Slackイベントからサボり提案までを疎結合のサーバーレス構成で実装しています。  
> Bedrockは文章生成ではなく、Tool Useで判定構造を固定するために使っています。  
> AI-DLCでは、人間が各フェーズの判断を承認し、さらにLean検証とOSS修正まで行いました。

## 4. 有効なプレゼン方針

### 4.1 勝つための一文

> SABOROUは、AIが科学的にあなたの判断力を奪うサービスです。

この一文に全スライドと全デモを寄せる。寄らない機能は削る。

### 4.2 見せるべき3つのWow

| Wow | 見せ方 | 目的 |

- 機能一覧の羅列

- ロードマップの細部

### 4.4 Q&Aで先回りすべき質問

| 質問 | 準備すべき回答 |

| これは人をダメにするのではなく最適化では？ | はい、最初は最適化に見えます。ただし、最適化の主体をAIへ移すことで、人間の判断機会を減らす設計です。 |

## 5. SABOROU SWOT分析

### 5.1 Strengths: 強み

| 強み | 根拠 | 評価 |
|---|---|---|
| テーマ解釈が深い | READMEと要件で「支援ツール」と「判断力退化」の二重構造を定義している | 便利さと危険さを両立できる |
| 技術素材が豊富 | Bedrock Tool Use、3エージェント、3バンドガント、SSE、Cognito、DynamoDB、CDK | 技術審査で戦える |
| 心理学5理論の差別化 | CEM、Identifiability、Sucker Effect、SDT、Expectancyを判定に接続 | 「科学的にサボる」という独自性 |
| AI-DLC実践証跡 | aidlc-docs、audit、Lean形式検証、OSS PR | AWS Summit文脈に強い |
| ゲーミフィケーションがテーマ直結 | AI依存度、称号、実績、ストリーク | 「ダメになっていく」を見せやすい |

### 5.2 Weaknesses: 弱み

| 弱み | 根拠 | リスク |
|---|---|---|
| ライブデモ信頼性が証明不足 | 401 handoff、E2E failed artifact | ステージ上で即失点 |
| UI/UXが情報過多 | 予選フィードバック、TaskDetailPageの要素過多 | 初見で価値が伝わらない |
| 決勝用ストーリーが未完成 | 現デモは5分予選用、技術資料中心 | 15分を使い切れない |
| モック/未完成機能が混在 | Manual、PvP、Guild、dummy Gantt fallback | 実装済み範囲を疑われる |
| スコープ資料が矛盾 | Slack-only予選資料と現在READMEの差分 | Q&Aで信頼を落とす |
| 運用監視が弱い | API Gatewayアクセスログ無効、通知不明 | 障害時に復旧できない |

### 5.3 Opportunities: 機会

| 機会 | 内容 | 活用方法 |
|---|---|---|
| 競合がプロダクト差別化勝負 | 技術突出チームが少ないというチーム分析 | 体験とストーリーで勝つ |
| AWS SummitのテーマがエージェンティックAI/サーバーレスに近い | 公式ページもAIエージェント、サーバーレスに言及 | SABOROUのAWS構成を自然に接続 |

### 5.4 Threats: 脅威

| S×T: 技術過多を防ぐ | Lean、CDK、OSS PRはデモ後の証拠として使い、冒頭では出さない。競合の演出力に対し、SABOROUは体験の強さで勝つ。 |
| W×O: UI弱点をデモ導線で隠す | 全機能を見せず、決勝用の1本道にする。UI全体の完成度より、ステージで見える導線の完成度を上げる。 |
| W×T: デモ障害を最優先で潰す | E2E failed、401、アクセスログ無効は、決勝に残すと即死リスク。新機能追加より優先する。 |

## 7. 優先戦略トップ3

### 1位: 決勝デモを1本化する

**内容**: Slack依頼、文脈読解、3バンドガント、クイック返信、AI依存度上昇だけに絞る。  
**理由**: 審査員が覚えるのは機能一覧ではなく、1つの体験である。  
**成功条件**: 15分プレゼン後、審査員が「AIが判断力を奪うサービス」と一文で説明できる。

### 2位: 実AWS E2Eの緑化と証拠化

**内容**: 決勝デモ導線のE2Eを作り、成功ログ、スクリーンショット、録画、CloudWatchメトリクスを残す。  
**理由**: AWS上の動作デモが決勝要件であり、現状証跡は赤が残っている。  
**成功条件**: 本番URLで、同一デモデータを使った通し練習が3回連続成功する。

### 3位: 「最適化された人間」問題を武器化する

**内容**: 予選で刺された「最適化では？」を、決勝では冒頭で自分たちから言う。  
**理由**: この反論を先回りできれば、SABOROUのテーマ解釈はむしろ深く見える。  
**成功条件**: Q&Aで同じ質問が来ても、審査員が「それは既にプレゼンで答えていた」と感じる。

## 10. 結論

SABOROUの勝ち筋は、ZKPやブロックチェーンを足すことではない。むしろ、これ以上の技術追加は危険である。

必要なのは、既にある技術を「審査員が使いたくなる体験」に変換すること。そして「人をダメにする」の解釈を、便利な最適化ではなく、AIへの快適な判断委譲として見せ切ること。

決勝で言うべきことはシンプル。

> AIは仕事を速くするだけではありません。  
> 判断そのものを奪うこともできます。  
> SABOROUは、その退化をいちばん気持ちよく体験できるサービスです。

この一文に、プロダクト、デモ、AWS構成、AI-DLC、Q&Aをすべて接続する。そこまで絞れれば、SABOROUは決勝でかなり強い。
